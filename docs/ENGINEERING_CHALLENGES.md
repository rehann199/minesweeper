# Engineering Challenges

Each entry follows Problem, Approach, Outcome and, where relevant, Trade-off. All descriptions are conceptual; no production identifiers or tuning values are published.

## 1. One game design, four platforms

- **Problem:** ship the same game to phones, Android TV and Apple TV, where input, layout, store rules and ad policy differ, without letting the rules drift apart.
- **Approach:** keep the rules in a pure logic layer that has no UI or platform dependencies. The mobile Flutter app builds for Android and iOS. A fork of it targets Android TV with a D-pad focus model and an unchanged domain layer. Apple TV is native Swift and SwiftUI with a hand-ported logic layer, chosen to get first-class Siri Remote handling and a lean, dependency-free app.
- **Outcome:** identical game semantics on every platform, with platform-native input. Of the Dart source paths that exist in both Flutter apps, 10 of 59 are byte-identical and include all of the game rules.
- **Trade-off:** UI and services are duplicated (49 diverged paths) and there is no shared package. Fixing a rule bug means editing up to three places.

## 2. A first move that cannot lose

- **Problem:** the opening click must be safe, but pre-generating the board lets layouts be inspected, and re-rolling after the click is awkward.
- **Approach:** generate lazily on the first reveal. Exclude the tapped cell and its eight neighbours, then draw random positions until the mine count is met (rejection sampling). Custom boards cap the mine count so the exclusion zone always fits. The Swift port adds an attempt cap and clamps the mine count as a guard against an unchecked configuration.
- **Outcome:** the first reveal is always a zero-cell that opens an area, and flagging before the first reveal is rejected so the board is never generated by a flag.
- **Trade-off:** the Dart loop has no attempt cap and depends on checked input. A property test over random board sizes would be the natural way to pin this down.

## 3. Cascading reveals without recursion

- **Problem:** revealing a zero-cell can open most of a board; recursion risks deep call stacks and is awkward to reason about.
- **Approach:** an explicit stack with a visited set, run inside a pure function that returns a fresh copy of the grid (cells are immutable value objects) and a revealed-cell count. Numbered cells reveal but do not expand; flagged cells block expansion.
- **Outcome:** deterministic, easy-to-port logic. The Swift port uses integer keys instead of string keys.
- **Trade-off:** every action copies the grid. That is fine at a few hundred cells but is not the most efficient structure.

## 4. Touch: tap, hold and pan on the same cell

- **Problem:** on a zoomable board, a finger touching a cell might be starting a tap, a long-press or a pan. Reveal-on-tap-down fired while the gesture was undecided and detonated mines when the player meant to flag or pan.
- **Approach:** reveal only on tap-up, flag on long-press, capture the global tap position so effects start at the right place under any zoom and pan, and reset the interactive viewer to its identity transform when fully zoomed out. A widget test asserts that hold-to-flag never also reveals.
- **Outcome:** reveal, flag and pan stay distinct on boards that need zoom. The cost is a very small latency on reveal because the action waits for finger release.

## 5. Android TV: a focus model for a grid

- **Problem:** a D-pad has no pointer. The board needs a visible cursor, a way to reach the header controls, and a flag action even though the remote has one select button.
- **Approach:** one root focus node handles key events. A hand-managed cursor moves over two areas (grid and header), clamps at edges and enters the header when moving up from the top row. Select-down starts a hold timer: expiry flags, an earlier release reveals, and release after expiry is suppressed. Back and escape are always handled and ask for confirmation; dialogs suppress game input; other screens ignore key-repeat events. Focus telemetry is throttled and de-duplicated.
- **Outcome:** the full game, including flagging, hints and pause, is playable from a remote without touch.
- **Trade-off:** the cursor is bespoke rather than using the framework's focus traversal, so accessibility tooling does not see individual cells.

## 6. Apple TV: avoiding the focus engine for the board

- **Problem:** the SwiftUI focus engine is a poor fit for hundreds of cells, and a standard button gives no hold gesture on the Siri Remote select button.
- **Approach:** a transparent, always-focusable UIKit view receives select press begin and end events. A timer of about half a second decides tap versus hold, and a hold suppresses the following release. SwiftUI move, play-pause and exit commands supply movement and pause. The board highlight is a custom cursor. A blocked flag disables input while modal dialogs are shown.
- **Outcome:** one input abstraction reused across the other Apple TV screens, so every screen shares the same press semantics.
- **Trade-off:** the custom cursor means the app does not benefit from system focus effects on the board.

## 7. Bomb recovery without corrupting state

- **Problem:** let a player continue after a mine through a reward flow while keeping score, flag counts and win detection correct.
- **Approach:** a loss stops the timer but keeps mines hidden. Recovery converts the exploded mine into a flag, restarts the timer, applies a score penalty and increments a per-game counter capped at two. The reward gate resolves once per request and the recovery itself is re-checked against the per-game limit, so a repeated callback cannot grant two recoveries. The mobile app snapshots the board before the blast so a revive can reassemble the same image.
- **Outcome:** the win condition stays valid because flagged cells count as unrevealed, and the UI shows a shatter and reassemble animation.
- **Note:** the reward flow is wired on Mobile and Android TV. The Apple TV app ports the logic transition, but its dialog offers restart or exit.

## 8. Monetisation that cannot block launch

- **Problem:** an app-open ad and a consent prompt can stall startup on slow networks, and a stalled launch is a poor experience.
- **Approach:** an instant splash, then staged initialisation with timeouts on storage and Firebase, native entitlement sync (falling back to the cached value), consent, remote ad configuration, SDK init and an on-demand ad. A hard cap on the gate pauses during user-facing prompts. Premium users skip the ad path. Each stage has a performance trace.
- **Outcome:** launch is bounded and measurable, and premium users never wait on ads.

## 9. Remote kill-switches that fail closed

- **Problem:** a misbehaving ad placement must be switchable off without an app release, and without user accounts.
- **Approach:** per-placement and global booleans in one remote document, read once and then followed through a live listener. The gate treats any unconfirmed state as off.
- **Outcome:** per-placement control without a custom backend, and ads that stay off when configuration is unknown. A test suite covers the configuration logic.

## 10. Platform-correct billing

- **Problem:** purchase edge cases (restores, consumables, subscription trial offers, delayed transactions) change faster than cross-platform plugins.
- **Approach:** native Kotlin and Swift managers behind method and event channels on the Flutter apps; StoreKit 2 directly on Apple TV. Hint packs are consumed after grant, unlocks are acknowledged, purchases are queried on connect to restore, and a trial offer is detected from the pricing phases. Native entitlement overwrites the cached premium flag at startup, and a network error never revokes ownership.
- **Outcome:** premium state converges at launch. Billing product parsing is covered by tests on mobile.
- **Trade-off:** there is no server-side receipt verification, and hint balances are client-held, so server-side entitlement verification would be a natural next step.

## 11. Telemetry that does not flood

- **Problem:** board touches and D-pad moves can produce hundreds of events per session.
- **Approach:** accumulate touch counts and blocked-input reasons in memory and emit one summary per game; throttle and de-duplicate TV focus events; sanitise names and payloads to fit analytics limits; queue events until Firebase is ready; collection is off until explicitly enabled.
- **Outcome:** analytics stay useful and cheap, with tests for the sanitiser, coverage and the touch tracker.

## 12. A stranded pause

- **Problem:** an app-lifecycle sequence of inactive, hidden and paused could leave the game paused after the user returned.
- **Approach:** a latch records that the app itself paused the game on the first background event and resumes only in that case, so later lifecycle events cannot strand it. A widget test reproduces the sequence.
- **Outcome:** consistent pause and resume on mobile and Android TV.

## What would come next

Shared rules package with unit and property tests, a consolidated Flutter package, game-state restore, board semantics for assistive technology, server-side entitlement verification, and a measured performance pass on large boards, especially on the TV cell widget.
